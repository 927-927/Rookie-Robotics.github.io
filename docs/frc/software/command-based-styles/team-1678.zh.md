# 1678 队 { #team-1678 }

1678 队按常规的方式使用基于命令的代码，一直搭建到整台机器人。每个子系统是一个电机，或者一组总是一起动的电机，它只需要一个目标：一个**设定值**（setpoint）。机器人的行为都写在命令里。按钮运行一个命令，给它需要的子系统发送设定值，调度器保证两个命令永远不会同时驱动同一个电机。

这一页看他们 2026 年（比赛项目 REBUILT）代码里的两件事：子系统是怎样组织的，以及一个命令是怎样从按钮一路传到电机的。它和 [2910 队](team-2910.md)的做法几乎正好相反，所以这一页会边讲边比较两者。

!!! info "关于本页的代码"

    本页用到的名字来自 1678 队 2026 年的机器人代码，GitHub 上的 [frc1678/C2026-Public](https://github.com/frc1678/C2026-Public)。这个仓库没有为队伍自己的代码附带许可证，所以本页代码窗口里展示的是为本页编写的简短示意代码，而不是 1678 的原文件。它们使用 1678 的类名和方法名，但省略了很多内容。要阅读真实的代码，请点击每个窗口下面的链接。

## 子系统是怎样组织的 { #how-the-subsystems-are-organized }

### 子系统基类 { #subsystem-bases }

和 2910 一样，1678 只把电机代码写一次，作为 [`frc/lib/bases`](https://github.com/frc1678/C2026-Public/tree/main/src/main/java/frc/lib/bases) 里的基类，每个子系统都 `extends` 其中一个。区别在于多了一层共享：每种机构都有同一个父类 `MotorSubsystem`。

#### 子系统下面的各层 { #the-layers-under-a-subsystem }

- **机器人子系统**非常小。[`Hood.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/hood/Hood.java) 大约只有 20 行：几个命名的设定值，比如 `Hood.STOW`，再加一个构造函数。其他一切都来自它的基类。
- **基类**存放电机代码。`MotorSubsystem` 持有 `io`，每次循环读取传感器，并给每个子系统提供它的命令 `setpointCommand()` 和 `followSetpointCommand()`。它的子类只增加各自那种机构特有的东西。
- **`MotorIO`** 是一个记住当前设定值的抽象类。`applySetpoint()` 是让电机动起来的唯一公开方法：各控制模式对应的方法都是 `protected`，外部无法调用。
- **IO 实现**做真正的工作。`MotorIOTalonFX` 把请求发给 TalonFX。`MotorIOTalonFXSim` 继承它，把仿真电机的电压输入物理模型，比如调角板用的 `PivotSim`。每个子系统的常量文件用 `Robot.isReal()` 选择其中一个。

和 [2910 的各层](team-2910.md#the-layers-under-a-subsystem)比较一下：在那里，滚轮基类和伺服基类是兄弟关系，各自持有自己的 `io`。在这里，`io` 只由共同的父类持有一次。

#### 设定值自带控制模式 { #setpoints-carry-the-control-mode }

在 2910 的代码里，控制模式就是方法名：调角板用 `setMotionMagicSetpoint()`，滚轮用一个速度 setter。所以滚轮基类和伺服基类必须提供不同的方法。在 1678 的代码里，控制模式放在目标值里面。一个 `Setpoint` 包含三样东西：

- **控制模式**：`IDLE`、`VOLTAGE`、`MOTIONMAGIC`、`VELOCITY`、`DUTY_CYCLE` 或 `POSITIONPID`。
- **目标值**，比如一个角度或一个速度。
- **要调用** `MotorIO` 上的哪个方法来达到目标。

用工厂方法创建它，比如 `Setpoint.withMotionMagicSetpoint(angle)` 或 `Setpoint.withVelocitySetpoint(speed)`，再在子系统上给它起个名字：`Hood.STOW`、`Shooter.FERRY`。一个 `applySetpoint(Setpoint)` 就能处理所有模式，所以父类可以持有全部电机代码，而不用关心收到的是哪种模式。

**从动电机也是同样的思路。**它们列在电机的 IO 配置里，由 `MotorIOTalonFX` 让它们跟随主电机。所以发射机构只是一个普通的飞轮子系统，它根本不知道自己有不止一个电机。2910 则是用单独的 `WithFollowers` 基类来处理。

#### 基类的种类 { #the-kinds-of-base }

- **`MotorSubsystem`** 是父类，也可以单独使用，用于普通的滚轮：`FeederRollers`、`HopperRollers` 和 `IntakeRollers`。
- **`FlywheelMotorSubsystem`** 增加了 `nearVelocity()` 和一个"已转到速"（spun up）的检查。`Shooter` 和 `TunnelRollers` 使用它。
- **`ServoMotorSubsystem`** 增加了 `nearPosition()`、软限位、归零，以及 `setpointCommandWithWait()`，它会先应用一个设定值，然后等机构到位。`Hood`、`IntakeDeploy` 和 `Climber` 使用它。
- **`CoupledServoMotorSubsystem`** 是一种伺服，能补偿另一个机构对它的带动。2026 年的机器人上没有用到它。

另外还有 LED（`LightsSubsystem`）和摄像头（`CameraSubsystem`）的基类。

和 2910 的滚轮、伺服不同，这些种类在能接收什么指令上没有区别：任何一种都能接收任何设定值。它们的区别在于怎样判断自己是否到位了。飞轮问的是"我到这个速度了吗？"，伺服问的是"我到这个位置了吗？"。

**归零内置在伺服基类里。**当伺服收到一个靠近零点位置的设定值时，它会用设定的归零电压驱动，直到不再移动，然后把那里设为零点。上面的层什么都不用管。

```java linenums="1"
public class MotorSubsystem<IO extends MotorIO> extends SubsystemBase {
    protected final IO io;

    public MotorSubsystem(IO io, String name) {
        super(name);
        this.io = io;
    }

    @Override
    public void periodic() {
        io.updateInputs(); // 读取电机的传感器
        // 未展示：日志，以及从仪表盘调 PID
    }

    public Angle getPosition() {
        return io.getPosition();
    }

    public AngularVelocity getVelocity() {
        return io.getVelocity();
    }

    public Setpoint getSetpoint() {
        return io.getSetpoint();
    }

    public void applySetpoint(Setpoint setpoint) {
        io.applySetpoint(setpoint);
    }

    // 应用一次设定值，然后结束
    public Command setpointCommand(Setpoint setpoint) {
        return runOnce(() -> applySetpoint(setpoint));
    }

    // 每次循环都重新应用最新的设定值
    public Command followSetpointCommand(Supplier<Setpoint> supplier) {
        return run(() -> applySetpoint(supplier.get()));
    }
}
```

<div class="vscode__note" markdown>
**共同的父类。**每个电机子系统都拥有这些。它的两个命令是用子系统自己的 `runOnce()` 和 `run()` 创建的，所以它们会**占用**这个子系统：如果另一个命令想要这个电机，调度器会取消较早的那个。[真实的文件](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/lib/bases/MotorSubsystem.java)里还有其他 getter、日志和调参功能。

```java linenums="1"
public class FlywheelMotorSubsystem<IO extends MotorIO>
        extends MotorSubsystem<IO> {
    protected final AngularVelocity epsilonThreshold;
    protected final Debouncer debouncer;

    // 未展示：构造函数，它接收多接近算"到位"，
    // 以及 spunUpDebounced() 要等多久

    public boolean nearVelocity(AngularVelocity target) {
        double error = getVelocity().minus(target).baseUnitMagnitude();
        return Math.abs(error) <= epsilonThreshold.baseUnitMagnitude();
    }

    // 是否达到了当前设定值要求的速度？
    public boolean spunUp() {
        Setpoint setpoint = getSetpoint();
        return setpoint.mode.isVelocityControl()
                && nearVelocity(RadiansPerSecond.of(setpoint.baseUnits));
    }

    // 和 spunUp() 一样，但要持续为真一小段时间才算
    public boolean spunUpDebounced() {
        return debouncer.calculate(spunUp());
    }
}
```

<div class="vscode__note" markdown>
**飞轮基类。**它只增加了检查：飞轮是否到了某个速度，以及是否到了设定值要求的速度？消抖版本能防止一次碰巧的读数被算进去。[真实的文件](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/lib/bases/FlywheelMotorSubsystem.java)里每种检查都还有几个其他版本。

```java linenums="1"
public class ServoMotorSubsystem<IO extends MotorIO>
        extends MotorSubsystem<IO> {
    protected final Angle epsilonThreshold;
    private ServoHomingConfig homingConfig;
    private boolean needsToHome = true;
    private boolean homing = false;

    // 未展示：构造函数，带归零和不带归零两种

    public boolean nearPosition(Angle target) {
        double error = getPosition().minus(target).baseUnitMagnitude();
        return Math.abs(error) <= epsilonThreshold.baseUnitMagnitude();
    }

    // 应用一个设定值，然后等机构到位
    public Command setpointCommandWithWait(Setpoint setpoint) {
        Angle target = Radians.of(setpoint.baseUnits);
        return Commands.waitUntil(() -> nearPosition(target))
                .deadlineFor(setpointCommand(setpoint));
    }

    @Override
    public void periodic() {
        super.periodic();

        // 被要求回零点，而且已经很近了？那就归零
        if (needsToHome && setpointNearHome() && nearHomingLocation()) {
            homing = true;
        }

        if (homing) {
            // 轻轻地推向机械限位
            io.applySetpoint(Setpoint.withVoltageSetpoint(
                    homingConfig.kHomingVoltage));

            // 未展示：stoppedForAWhile()，当机构几乎静止
            // 持续 kHomingTimeout 后返回 true
            if (stoppedForAWhile()) {
                setCurrentPosition(homingConfig.kHomePosition);
                homing = false;
                needsToHome = false;
            }
        }
    }

    @Override
    public void applySetpoint(Setpoint setpoint) {
        super.applySetpoint(setpoint);
        homing = false; // 新的设定值会停止归零
        // 要离开零点？那下次回来时再归零一次
        if (!setpointNearHome()) {
            needsToHome = true;
        }
    }
}
```

<div class="vscode__note" markdown>
**伺服基类。**除了位置检查，它每次循环还会自己处理归零。被要求回零点时，它用一个小电压推向机械限位，一旦停止移动，那个位置就成为它的零点。每次离开零点，回来时都会再归零一次。[真实的文件](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/lib/bases/ServoMotorSubsystem.java)还会在归零期间关闭软限位，并在归零后保持在零点位置。

### 创建子系统 { #creating-a-subsystem }

2910 在 `RobotContainer` 里构建每个子系统，并传入每个子系统需要的东西。1678 没有 `RobotContainer`。取而代之的是：

- **每个子系统自己创建自己。**它只有一个实例 `mInstance`，在任何代码第一次用到它时创建，比如 `Hood.mInstance`。
- **每个子系统旁边都有一个常量文件**，比如 [`HoodConstants.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/hood/HoodConstants.java)。里面有 TalonFX 的配置（传动比、电流限制、PID）、CAN ID 和从动电机、仿真设置以及各设定值的数值。它的 `getMotorIO()` 返回真实的 IO 或仿真的 IO。
- **构造函数把基类需要的东西传给它**：来自 `getMotorIO()` 的 IO、日志里用的名字、多接近算"到位"，以及对伺服来说，怎样归零。

`Robot.robotInit()` 设置按钮绑定，大多数子系统都是在这时第一次被用到，也就是在这时被创建的。

### 定义子系统 { #defining-subsystems }

1678 **每个电机一个子系统**，或者每组总是一起动的电机一个子系统。你指着机器人说"这是一个部分"的地方，往往有好几个子系统：吸取机构就分成控制臂的 `IntakeDeploy` 和控制滚轮的 `IntakeRollers`。

**为什么拆这么细？**一个命令只能占用整个子系统。把臂和滚轮分开后，一个命令可以让臂保持伸出，另一个命令同时转动滚轮，只有当两个命令想要同一个电机时，调度器才会介入。2910 能把它们合在一起，是因为决定谁拿到每个电机的是状态机，而不是调度器。

**中间没有别的层。**2910 的调角板和飞轮放在一个 `ShooterSubsystem` 下面。在这里，Superstructure 直接和发射机构、调角板打交道，就像和其他每个子系统一样。

**Superstructure 是一个命令库。**它是一个没有电机的子系统。[`Superstructure.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/superstructure/Superstructure.java) 里有大约 50 个返回命令的函数，比如 `intake()`、`shoot()`、`tuck()` 和 `fenderShot()`，总共约 1,100 行。

**射击的计算放在单独的类里。**[`Shooting`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/shooting/Shooting.java) 不是子系统。它根据机器人的位置和运动状态算出射击参数，Superstructure 向它要最新的设定值。2910 则是在它的 SuperStructure 里做这些计算。

### 子系统怎样驱动电机 { #how-a-subsystem-drives-its-motor }

这里没有状态机：任何地方都没有 `WantedState` 或 `SystemState`。Superstructure 有一个小小的 `State` 枚举（`IDLE`、`OUTTAKE`、`SHOOT`），但它只是一个标记。子系统只做它最后收到的设定值要求的事：

1.  一个命令应用一个设定值。
2.  `MotorIO` 记住它，并把它发给 TalonFX 一次。
3.  TalonFX 自己运行控制回路，比如 Motion Magic 或速度 PID，并一直保持这个设定值，直到收到新的设定值。

所以固定的目标在机器人代码里不需要循环。`setpointCommand()` 是一个 `runOnce`：它应用设定值，并在同一个循环里结束。对于一直在变的目标，`followSetpointCommand()` 接收一个函数，每次循环都重新应用它的结果。射击时，发射机构的转速和调角板的角度就是用这种方式跟着 `Shooting` 的最新数值走。

子系统的 `periodic()` 不会让任何东西动起来。它读取传感器、记录日志，并应用从仪表盘调好的 PID 参数。伺服归零是唯一会自己设置电机的东西。

**协调靠的是命令的顺序。**1678 不用状态转换，而是用 WPILib 的命令组合器来搭建每一个动作：

- `sequence(a, b)`：先做 `a`，再做 `b`。
- `parallel(a, b)`：两个同时做。
- `waitUntil(condition)`：等到某件事为真，比如"发射机构已转到速"。
- `either(a, b, condition)`：根据条件做 `a` 或 `b`。

比如，`intake()` 同时放下臂并转动滚轮，等到球道可以预装填时，再进行预装填。2910 会把这里的每一步都写成一次状态转换。

## 命令是怎样运行的 { #how-a-command-runs }

[`ControlBoard.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/controlboard/ControlBoard.java) 存放按钮绑定，分成好几套，`configureBindings()` 打开他们想用的那一套。按钮到电机有两种路径。

### 测试时 { #while-testing }

**触发器 → 改变设定值 → 子系统响应。**`bringupControls()` 把按钮直接绑定到子系统的设定值上，比如左扳机绑定 `Shooter.mInstance.setpointCommand(Shooter.FERRY)`，这样每个电机都可以单独检查。`jogControls()` 让按钮在最小值和最大值之间小步调高或调低子系统的设定值，用来找到合适的数值。

比赛时，这几套绑定在 `configureBindings()` 里是注释掉的。

### 比赛中 { #in-a-match }

**触发器 → Superstructure 函数 → 改变设定值 → 子系统响应。**`driverControls()` 把按钮绑定到 Superstructure 的函数上。每个函数返回一个由各子系统的命令组合而成的命令，由调度器来运行。

#### 例子：扣下右扳机 { #example-pulling-the-right-trigger }

右扳机是边开边射。它同时运行两个命令：负责各机构的 `Superstructure.shoot()`，以及 `Shooting.followShootOnTheMoveRequest()`，后者在操作手驾驶时让机器人转向目标。在 `shoot()` 里面：

1.  **瞄准。**发射机构和调角板每次循环都跟着 `Shooting` 的最新设定值走。机器人在 trench 里时，调角板会收起来。
2.  **等待。**一个 `waitUntil(...)` 会一直等，直到射击对准了、发射机构和调角板都到了目标值，并且机器人移动得足够慢。
3.  **送料。**料仓、球道和送料滚轮开始把燃料球送进发射机构。

**松开扳机**会通过 `onFalse` 运行另一个 Superstructure 命令：如果操作手还在吸取，就运行 `stopShooting()`，否则运行 `idle()`。无论哪种情况，调角板都会回到 `STOW`。

**两个按钮都想要同一个子系统时**：调度器会取消较早的那个命令，因为每个子系统命令都会占用它的子系统。有些命令还会随着按钮停止：左扳机只在按住时运行 `intake()`。

**自动阶段**也是用同样的组件搭起来的。每个自动程序都是一个单独的类，比如 `LeftSweep`，把 Choreo 路径和射击命令串成一个序列。

`Robot.java` 会在每个命令启动、结束或被打断时记录日志，所以从日志里可以看到任意时刻有哪些命令在运行。

public class ControlBoard extends SubsystemBase {
    public static final ControlBoard mInstance = new ControlBoard();

    private CommandXboxController driver =
            ControlBoardConstants.mDriverController;
    private CommandXboxController operator =
            ControlBoardConstants.mOperatorController;

    // 在 Robot.robotInit() 里调用一次
    public void configureBindings() {
        // 未展示：底盘的默认命令，用于摇杆
        driverControls();
        // bringupControls();
        // jogControls();
    }

    // 测试：每个按钮给一个子系统一个设定值
    public void bringupControls() {
        driver.leftTrigger().onTrue(
                Shooter.mInstance.setpointCommand(Shooter.FERRY));
        driver.rightTrigger().onTrue(
                Shooter.mInstance.setpointCommand(Shooter.IDLE));
        operator.a().onTrue(
                Hood.mInstance.setpointCommand(Hood.STOW));
        // ……以此类推，每个子系统都有
    }

    // 比赛中：每个按钮运行一个 Superstructure 命令
    public void driverControls() {
        driver.leftTrigger()
                .onTrue(Superstructure.mInstance.intake()
                        .onlyWhile(driver.leftTrigger()))
                .onFalse(Superstructure.mInstance.idleIntake());

        driver.rightTrigger(0.1)
                .onTrue(Commands.parallel(
                        Superstructure.mInstance.shoot(),
                        Shooting.mInstance
                                .followShootOnTheMoveRequest()));
        driver.rightTrigger(0.1)
                .onFalse(Commands.either(
                                Superstructure.mInstance.stopShooting(),
                                Superstructure.mInstance.idle(),
                                () -> driver.leftTrigger().getAsBoolean())
                        .alongWith(
                                Hood.mInstance.setpointCommand(Hood.STOW)));

        driver.a().onTrue(Superstructure.mInstance.tuck());
        driver.y().onTrue(Superstructure.mInstance.fenderShot());
        // 未展示：另外大约 20 个绑定，以及右肩键，
        // 它会改变扳机和 Y 的功能
    }
}

```java linenums="1"
public class Superstructure extends SubsystemBase {
    public static final Superstructure mInstance = new Superstructure();

    // 把各个臂同时收起来
    public Command tuck() {
        return Commands.parallel(
                IntakeDeploy.mInstance.setpointCommand(
                        IntakeDeploy.STOWED_SETPOINT),
                Climber.mInstance.setpointCommand(Climber.STOW),
                Hood.mInstance.setpointCommand(Hood.STOW));
    }

    // 放下吸取机构并转动它，然后预装填球道
    public Command intake() {
        return Commands.sequence(
                Commands.parallel(
                        IntakeDeploy.mInstance.setpointCommand(
                                IntakeDeploy.DEPLOYED_SETPOINT),
                        IntakeRollers.mInstance.setpointCommand(
                                IntakeRollers.INTAKE)),
                Commands.waitUntil(
                        () -> prefillReady() && !prefillDone()),
                prefillBallTunnel());
    }

    // 为贴着 fender 射击转到速，然后送料
    public Command fenderShot() {
        return Commands.sequence(
                Shooter.mInstance.setpointCommand(
                        SuperstructureConstants.getShooterSetpointFender()),
                Hood.mInstance.setpointCommand(
                        SuperstructureConstants.getHoodSetpointFender()),
                Commands.waitUntil(() -> spunUp()),
                FeederRollers.mInstance.setpointCommand(
                        FeederRollers.FEED_VOLTAGE),
                HopperRollers.mInstance.setpointCommand(
                        HopperRollers.INTAKE));
    }

    // 未展示：另外大约 45 个，比如 shoot()、idle() 和 stopShooting()
}
```

<div class="vscode__note" markdown>
**由命令组成的命令。**每个函数返回一个命令，用 `parallel`、`sequence` 和 `waitUntil` 把各子系统自己的命令组合起来。`setpointCommand` 一应用完就结束，所以在 `fenderShot()` 里，发射机构和调角板在同一个循环里拿到设定值，再由 `waitUntil` 让送料等到它们到位。[真实的文件](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/superstructure/Superstructure.java)在 `fenderShot()` 里还会让球道滚轮转起来。

### 和 2910 比较 { #compared-with-2910 }

| | 2910 队 | 1678 队 |
|---|---|---|
| **按钮运行的是** | 一个设置期望状态然后马上结束的命令 | 一个占用它要驱动的子系统的 Superstructure 命令 |
| **由谁设置电机** | 每个子系统的 `periodic()`，每次循环 | 正在运行的命令；TalonFX 保持每个设定值 |
| **两个按钮都想要同一个子系统时** | 最后设置的期望状态胜出 | 调度器打断较早的那个命令 |
| **子系统** | 机器人的每个部分一个，比如吸取机构 | 每个电机或电机组一个 |
| **子系统的层级** | SuperStructure → Shooter → Hood | Superstructure → 每个子系统 |
| **机器人的逻辑放在哪里** | 状态机里 | Superstructure 里命令的顺序 |

这样做的好处：

- **每个动作都能从上往下读。**`intake()` 和 `fenderShot()` 读起来就像菜谱：做这个，等那个，然后做下一件事。
- **调度器保护着电机。**两个命令永远不能同时驱动同一个子系统。
- **加一个机构的工作量很小。**只需要一个短小的类和一个常量文件。

代价是：

- **大命令会变得难读。**`shoot()` 是一个大约 90 行长的命令，命令里面套着命令。
- **没有一个统一的状态可看。**机器人在做什么取决于哪些命令正在运行，所以他们改为记录每一个命令。
- **任何代码都能动任何东西。**任何代码都能访问 `Shooter.mInstance`。只让 Superstructure 来做这件事，是一条只能靠队伍自己遵守的规则。

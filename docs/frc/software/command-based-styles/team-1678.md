# Team 1678

Team 1678 uses command-based code the usual way, built up to a whole robot.
Each subsystem is one motor, or a group of motors that always move
together, and all it takes is a target: a **setpoint**. The robot's
behavior lives in the commands. A button runs a command that gives
setpoints to the subsystems it needs, and the scheduler makes sure two
commands never drive the same motor.

This page looks at two things in their 2026 code, for the game REBUILT: how
the subsystems are organized, and how a command gets from a button to a
motor. It's almost the opposite of [Team 2910's](team-2910.md) approach, so
the page compares the two as it goes.

    The names on this page come from Team 1678's 2026 robot code,

## How the subsystems are organized

### Subsystem bases

Like 2910, 1678 writes the motor code once, as base classes in
[`frc/lib/bases`](https://github.com/frc1678/C2026-Public/tree/main/src/main/java/frc/lib/bases),
and every subsystem `extends` one of them. The difference is one more level
of sharing: every kind of mechanism has the same parent class,
`MotorSubsystem`.

#### The layers under a subsystem

There are five layers, from a robot subsystem down to its motor, and each
layer only talks to the one below it:

- **Robot subsystems** are tiny.
  [`Hood.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/hood/Hood.java)
  is about 20 lines: a few named setpoints, like `Hood.STOW`, and a
  constructor. Everything else comes from its base.
- **Base classes** hold the motor code. `MotorSubsystem` holds the `io`,
  reads the sensors every loop, and gives every subsystem its commands,
  `setpointCommand()` and `followSetpointCommand()`. Its children only add
  what's special about their kind of mechanism.
- **`MotorIO`** is an abstract class that remembers the current setpoint.
  `applySetpoint()` is the only public way to move the motor: the methods
  for each control mode are `protected`, so nothing outside can call them.
- **The IO implementations** do the real work. `MotorIOTalonFX` sends the
  request to the TalonFX. `MotorIOTalonFXSim` extends it and feeds the
  simulated motor's voltage into a physics model, like `PivotSim` for the
  hood. Each subsystem's constants file picks one with `Robot.isReal()`.

Compare this with
[2910's layers](team-2910.md#the-layers-under-a-subsystem): there, the
roller and servo bases are siblings, and each holds its own `io`. Here the
`io` is held once, by the shared parent.

#### Setpoints carry the control mode

In 2910's code, the control mode is the method name:
`setMotionMagicSetpoint()` for the hood, a velocity setter for a roller.
So the roller and servo bases have to offer different methods. In 1678's
code, the control mode is inside the target. A `Setpoint` holds three
things:

- **The control mode**: `IDLE`, `VOLTAGE`, `MOTIONMAGIC`, `VELOCITY`,
  `DUTY_CYCLE` or `POSITIONPID`.
- **The target**, like an angle or a speed.
- **What to call** on the `MotorIO` to get there.

You make one with a factory method, like
`Setpoint.withMotionMagicSetpoint(angle)` or
`Setpoint.withVelocitySetpoint(speed)`, and give it a name on the
subsystem: `Hood.STOW`, `Shooter.FERRY`. One `applySetpoint(Setpoint)`
handles every mode, so the parent class can hold all the motor code
without caring which mode it gets.

**Followers work the same way.** They're listed in the motor's IO config,
and `MotorIOTalonFX` makes them follow the main motor. So the shooter is a
plain flywheel subsystem that never knows it has more than one motor. 2910
uses separate `WithFollowers` base classes instead.

#### The kinds of base

- **`MotorSubsystem`**, the parent, is also used on its own, for plain
  rollers: `FeederRollers`, `HopperRollers` and `IntakeRollers`.
- **`FlywheelMotorSubsystem`** adds `nearVelocity()` and a "spun up"
  check. Used by `Shooter` and `TunnelRollers`.
- **`ServoMotorSubsystem`** adds `nearPosition()`, soft limits, homing and
  `setpointCommandWithWait()`, which applies a setpoint and then waits until
  the mechanism gets there. Used by `Hood`, `IntakeDeploy` and `Climber`.
- **`CoupledServoMotorSubsystem`** is a servo that corrects for another
  mechanism moving it. Nothing on the 2026 robot uses it.

There are also bases for the LEDs (`LightsSubsystem`) and the cameras
(`CameraSubsystem`).

Unlike 2910's roller and servo, the kinds don't differ in what they can be
asked to do: any of them takes any setpoint. They differ in how they check
whether they got there. A flywheel asks "am I at this speed?", and a servo
asks "am I at this position?".

**Homing is built into the servo base.** When a servo is sent to a setpoint
near its home position, it drives at a set homing voltage until it stops
moving, then sets that as home. Nothing above it has to ask.

```java linenums="1"
public class MotorSubsystem<IO extends MotorIO> extends SubsystemBase {
    protected final IO io;

    public MotorSubsystem(IO io, String name) {
        super(name);
        this.io = io;
    }

    @Override
    public void periodic() {
        io.updateInputs(); // read the motor's sensors
        // Not shown: logging, and PID tuning from the dashboard
    }

    public Angle getPosition() {
        return io.getPosition();
    }

    public AngularVelocity getVelocity() {
        return io.getVelocity();
    }

    public Setpoint getSetpoint() {
        return io.getSetpoint();
    }

    public void applySetpoint(Setpoint setpoint) {
        io.applySetpoint(setpoint);
    }

    // Apply the setpoint once, then end
    public Command setpointCommand(Setpoint setpoint) {
        return runOnce(() -> applySetpoint(setpoint));
    }

    // Apply the latest setpoint again every loop
    public Command followSetpointCommand(Supplier<Setpoint> supplier) {
        return run(() -> applySetpoint(supplier.get()));
    }
}
```

they **require** the subsystem: if another command wants this motor, the
scheduler cancels the older one.

```java linenums="1"
public class FlywheelMotorSubsystem<IO extends MotorIO>
        extends MotorSubsystem<IO> {
    protected final AngularVelocity epsilonThreshold;
    protected final Debouncer debouncer;

    // Not shown: the constructor, which takes how close counts
    // as "there" and how long spunUpDebounced() waits

    public boolean nearVelocity(AngularVelocity target) {
        double error = getVelocity().minus(target).baseUnitMagnitude();
        return Math.abs(error) <= epsilonThreshold.baseUnitMagnitude();
    }

    // At the speed the current setpoint asks for?
    public boolean spunUp() {
        Setpoint setpoint = getSetpoint();
        return setpoint.mode.isVelocityControl()
                && nearVelocity(RadiansPerSecond.of(setpoint.baseUnits));
    }

    // spunUp(), but only once it has stayed true for a moment
    public boolean spunUpDebounced() {
        return debouncer.calculate(spunUp());
    }
}
```

<div class="vscode__note" markdown>
**The flywheel base.** It only adds checks: is the flywheel at a speed,
and is it at the speed its setpoint asks for? The debounced version stops
one lucky reading from counting.
[The real file](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/lib/bases/FlywheelMotorSubsystem.java)
has a few more versions of each.

```java linenums="1"
public class ServoMotorSubsystem<IO extends MotorIO>
        extends MotorSubsystem<IO> {
    protected final Angle epsilonThreshold;
    private ServoHomingConfig homingConfig;
    private boolean needsToHome = true;
    private boolean homing = false;

    // Not shown: the constructors, with and without homing

    public boolean nearPosition(Angle target) {
        double error = getPosition().minus(target).baseUnitMagnitude();
        return Math.abs(error) <= epsilonThreshold.baseUnitMagnitude();
    }

    // Apply a setpoint, then wait until the mechanism gets there
    public Command setpointCommandWithWait(Setpoint setpoint) {
        Angle target = Radians.of(setpoint.baseUnits);
        return Commands.waitUntil(() -> nearPosition(target))
                .deadlineFor(setpointCommand(setpoint));
    }

    @Override
    public void periodic() {
        super.periodic();

        // Sent home, and close to it? Then home
        if (needsToHome && setpointNearHome() && nearHomingLocation()) {
            homing = true;
        }

        if (homing) {
            // Push gently into the hard stop
            io.applySetpoint(Setpoint.withVoltageSetpoint(
                    homingConfig.kHomingVoltage));

            // Not shown: stoppedForAWhile(), true once the mechanism
            // has been nearly still for kHomingTimeout
            if (stoppedForAWhile()) {
                setCurrentPosition(homingConfig.kHomePosition);
                homing = false;
                needsToHome = false;
            }
        }
    }

    @Override
    public void applySetpoint(Setpoint setpoint) {
        super.applySetpoint(setpoint);
        homing = false; // a new setpoint stops homing
        // Leaving home? Home again next time it comes back
        if (!setpointNearHome()) {
            needsToHome = true;
        }
    }
}
```

<div class="vscode__note" markdown>
**The servo base.** Besides the position checks, it homes by itself every
loop. When it's sent home, it pushes into the hard stop with a small
voltage, and once it stops moving, that spot becomes its zero. Every time
it leaves home, it homes again on the way back.
[The real file](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/lib/bases/ServoMotorSubsystem.java)
also turns the soft limits off while homing, and holds the home position
after.

### Creating a subsystem

2910 builds every subsystem in `RobotContainer` and passes in what each one
needs. 1678 has no `RobotContainer`. Instead:

- **Each subsystem makes itself.** It has one instance, `mInstance`,
  created the first time any code uses it, like `Hood.mInstance`.
- **Each subsystem has a constants file** next to it, like
  [`HoodConstants.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/hood/HoodConstants.java).
  It holds the TalonFX config (gearing, current limits, PID), the CAN IDs
  and followers, the simulation settings and the setpoint values. Its
  `getMotorIO()` returns the real IO or the simulated one.
- **The constructor passes the base what it needs**: the IO from
  `getMotorIO()`, a name for the logs, how close counts as "there", and,
  for a servo, how to home.

`Robot.robotInit()` sets up the button bindings, which is the first time
most subsystems get used, and so made.

### Defining subsystems

1678 makes **one subsystem per motor**, or per group of motors that always
move together. Where you'd point at one part of the robot, there are often
several subsystems: the intake is `IntakeDeploy` for the arm and
`IntakeRollers` for the rollers.

**Why so small?** A command can only require whole subsystems. With the
arm and the rollers apart, one command can hold the arm out while another
runs the rollers, and the scheduler only steps in when two commands want
the same motor. 2910 can group them because a state machine, not the
scheduler, decides who gets each motor.

**There's no layer in between.** 2910's hood and flywheel sit under a
`ShooterSubsystem`. Here, the Superstructure talks to the shooter and the
hood directly, like every other subsystem.

**The Superstructure is a library of commands.** It's a subsystem with no
motors.
[`Superstructure.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/superstructure/Superstructure.java)
has about 50 functions that each return a command, like `intake()`,
`shoot()`, `tuck()` and `fenderShot()`, in about 1,100 lines.

**The shooting math is in its own class.**
[`Shooting`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/shooting/Shooting.java)
isn't a subsystem. It works out the shot from where the robot is and how
it's moving, and the Superstructure asks it for the latest setpoints. 2910
does this math inside its SuperStructure.

### How a subsystem drives its motor

There are no state machines: no `WantedState` or `SystemState` anywhere.
The Superstructure has a small `State` enum (`IDLE`, `OUTTAKE`, `SHOOT`),
but it's only a flag. A subsystem does whatever its last setpoint says:

1.  A command applies a setpoint.
2.  `MotorIO` remembers it and sends it to the TalonFX once.
3.  The TalonFX runs the control loop itself, like Motion Magic or a
    velocity PID, and keeps holding the setpoint until a new one comes.

So a fixed target needs no loop in the robot code. `setpointCommand()` is
a `runOnce`: it applies the setpoint and ends in the same loop. For a
target that keeps changing, `followSetpointCommand()` takes a function and
applies its result again every loop. While shooting, the shooter's speed
and the hood's angle follow `Shooting`'s latest numbers this way.

A subsystem's `periodic()` doesn't move anything. It reads the sensors,
logs them, and applies PID values tuned from the dashboard. Servo homing is
the only thing that sets a motor on its own.

**The coordination is the order of the commands.** Instead of state
transitions, 1678 builds each action from WPILib's command combinators:

- `sequence(a, b)`: do `a`, then `b`.
- `parallel(a, b)`: do both at once.
- `waitUntil(condition)`: wait until something is true, like "the shooter
  is spun up".
- `either(a, b, condition)`: do `a` or `b`, depending on the condition.

For example, `intake()` deploys the arm and spins the rollers in parallel,
waits until the ball tunnel is ready to prefill, then prefills it. 2910
would write each of those steps as a state transition.

## How a command runs

[`ControlBoard.java`](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/controlboard/ControlBoard.java)
holds the button bindings, in several sets, and `configureBindings()` turns
on the set they want. There are two ways a button reaches a motor.

### While testing

**Trigger → change setpoint → subsystem responds.** `bringupControls()`
binds buttons straight to subsystem setpoints, like
`Shooter.mInstance.setpointCommand(Shooter.FERRY)` on the left trigger, so
each motor can be checked on its own. `jogControls()` lets buttons step a
subsystem's setpoint up and down in small steps, between a min and a max,
which helps find the right values.

These sets are commented out in `configureBindings()` for matches.

### In a match

**Trigger → Superstructure function → change setpoint → subsystem
responds.** `driverControls()` binds buttons to Superstructure functions.
Each one returns a single command built from the subsystems' commands, and
the scheduler runs it.

#### Example: pulling the right trigger

The right trigger shoots while driving. It runs two commands in parallel:
`Superstructure.shoot()` for the mechanisms, and
`Shooting.followShootOnTheMoveRequest()`, which turns the robot toward the
target while the driver drives. Inside `shoot()`:

1.  **Aim.** The shooter and the hood follow `Shooting`'s latest setpoints,
    every loop. The hood stows while the robot is inside the trench.
2.  **Wait.** A `waitUntil(...)` holds off until the shot is lined up, the
    shooter and hood are at their targets, and the robot is moving slowly
    enough.
3.  **Feed.** The hopper, tunnel and feeder rollers start moving fuel into
    the shooter.

**Letting go** runs another Superstructure command through `onFalse`:
`stopShooting()` if the driver is still intaking, `idle()` if not. The hood
goes back to `STOW` either way.

**Two buttons wanting the same subsystem**: the scheduler cancels the older
command, since every subsystem command requires its subsystem. Some
commands also stop with their button: the left trigger runs `intake()`
only while it's held.

**Autos** are built from the same pieces. Each auto is its own class, like
`LeftSweep`, that chains Choreo paths and shooting commands into one
sequence.

`Robot.java` logs every command when it starts, ends or is interrupted, so
a log shows which commands were running at any moment.

```java linenums="1"
public class ControlBoard extends SubsystemBase {
    public static final ControlBoard mInstance = new ControlBoard();

    private CommandXboxController driver =
            ControlBoardConstants.mDriverController;
    private CommandXboxController operator =
            ControlBoardConstants.mOperatorController;

    // Called once, from Robot.robotInit()
    public void configureBindings() {
        // Not shown: the drive's default command, for the sticks
        driverControls();
        // bringupControls();
        // jogControls();
    }

    // Testing: each button gives one subsystem one setpoint
    public void bringupControls() {
        driver.leftTrigger().onTrue(
                Shooter.mInstance.setpointCommand(Shooter.FERRY));
        driver.rightTrigger().onTrue(
                Shooter.mInstance.setpointCommand(Shooter.IDLE));
        operator.a().onTrue(
                Hood.mInstance.setpointCommand(Hood.STOW));
        // ...and so on, for every subsystem
    }

    // In a match: each button runs a Superstructure command
    public void driverControls() {
        driver.leftTrigger()
                .onTrue(Superstructure.mInstance.intake()
                        .onlyWhile(driver.leftTrigger()))
                .onFalse(Superstructure.mInstance.idleIntake());

        driver.rightTrigger(0.1)
                .onTrue(Commands.parallel(
                        Superstructure.mInstance.shoot(),
                        Shooting.mInstance
                                .followShootOnTheMoveRequest()));
        driver.rightTrigger(0.1)
                .onFalse(Commands.either(
                                Superstructure.mInstance.stopShooting(),
                                Superstructure.mInstance.idle(),
                                () -> driver.leftTrigger().getAsBoolean())
                        .alongWith(
                                Hood.mInstance.setpointCommand(Hood.STOW)));

        driver.a().onTrue(Superstructure.mInstance.tuck());
        driver.y().onTrue(Superstructure.mInstance.fenderShot());
        // Not shown: about 20 more bindings, and the right bumper,
        // which changes what the trigger and Y do
    }
}
```

<div class="vscode__note" markdown>
**Two sets of bindings.** In `bringupControls()`, a button goes straight to
one subsystem's setpoint. In `driverControls()`, a button runs a
Superstructure command, and letting go of a button runs another one.
`configureBindings()` turns on one set, and the others stay commented out.
[The real file](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/controlboard/ControlBoard.java)
also has the operator's controls and the rumble.

```java linenums="1"
public class Superstructure extends SubsystemBase {
    public static final Superstructure mInstance = new Superstructure();

    // Put the arms away, all at once
    public Command tuck() {
        return Commands.parallel(
                IntakeDeploy.mInstance.setpointCommand(
                        IntakeDeploy.STOWED_SETPOINT),
                Climber.mInstance.setpointCommand(Climber.STOW),
                Hood.mInstance.setpointCommand(Hood.STOW));
    }

    // Deploy and spin the intake, then prefill the ball tunnel
    public Command intake() {
        return Commands.sequence(
                Commands.parallel(
                        IntakeDeploy.mInstance.setpointCommand(
                                IntakeDeploy.DEPLOYED_SETPOINT),
                        IntakeRollers.mInstance.setpointCommand(
                                IntakeRollers.INTAKE)),
                Commands.waitUntil(
                        () -> prefillReady() && !prefillDone()),
                prefillBallTunnel());
    }

    // Spin up for a shot from the fender, then feed
    public Command fenderShot() {
        return Commands.sequence(
                Shooter.mInstance.setpointCommand(
                        SuperstructureConstants.getShooterSetpointFender()),
                Hood.mInstance.setpointCommand(
                        SuperstructureConstants.getHoodSetpointFender()),
                Commands.waitUntil(() -> spunUp()),
                FeederRollers.mInstance.setpointCommand(
                        FeederRollers.FEED_VOLTAGE),
                HopperRollers.mInstance.setpointCommand(
                        HopperRollers.INTAKE));
    }

    // Not shown: about 45 more, like shoot(), idle() and stopShooting()
}
```

<div class="vscode__note" markdown>
**Commands made of commands.** Each function returns one command built
from the subsystems' own commands, with `parallel`, `sequence` and
`waitUntil`. A `setpointCommand` ends as soon as it's applied, so in
`fenderShot()` the shooter and hood get their setpoints in the same loop,
and `waitUntil` holds the feeding back until they're there.
[The real file](https://github.com/frc1678/C2026-Public/blob/main/src/main/java/frc/robot/subsystems/superstructure/Superstructure.java)
also spins up the tunnel rollers in `fenderShot()`.

### Compared with 2910

| | Team 2910 | Team 1678 |
|---|---|---|
| **A button runs** | a command that sets a wanted state, then ends | a Superstructure command that requires the subsystems it moves |
| **What sets the motors** | each subsystem's `periodic()`, every loop | the running commands; the TalonFX holds each setpoint |
| **Two buttons wanting the same subsystem** | the wanted state set last wins | the scheduler interrupts the older command |
| **Subsystems** | one per part of the robot, like the intake | one per motor or motor group |
| **Layers of subsystems** | SuperStructure → Shooter → Hood | Superstructure → every subsystem |
| **Where the robot's logic lives** | the state machines | the order of the commands in the Superstructure |

What this gives them:

- **Each action reads top to bottom.** `intake()` and `fenderShot()` read
  like a recipe: do this, wait for that, then do the next thing.
- **The scheduler protects the motors.** Two commands can never drive the
  same subsystem at once.
- **Adding a mechanism is small.** It's a short class and a constants file.

What it costs:

- **Big commands get hard to read.** `shoot()` is one command about 90
  lines long, with commands nested inside commands.
- **There's no single state to look at.** What the robot is doing depends
  on which commands are running, so they log every command instead.
- **Anything can move anything.** Any code can reach `Shooter.mInstance`.
  Keeping that to the Superstructure is a rule the team has to keep
  themselves.

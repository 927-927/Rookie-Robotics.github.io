# Team 2910

Team 2910 uses command-based code, but almost none of their commands move a
motor. Each subsystem is a **state machine**, and a button press only tells
the robot which state you want. The robot works out the rest itself, every
loop.

## How the subsystems are organized

### Subsystem bases

Almost every mechanism on a robot either **spins** (an intake roller, a
flywheel) or **moves to a position** (an arm, a hood). 2910 writes the motor
code for each kind once, as a base class in `subsystems/base`, and every
real subsystem `extends` one of them.

<figure class="diagram" markdown="span">
  [![Roller: a spinning wheel pulling in fuel. It spins with no min or max position; controlled by velocity, duty cycle or voltage; coasts when stopped, no soft limits; used for intake rollers, the hopper and the flywheel. Servo: an arm on a pivot that moves between a min and a max, next to a hard stop. Controlled by position, Motion Magic, duty cycle or voltage; brakes when stopped, soft limits at min and max, can home; used for the intake arm and the hood](../../assets/images/software/team-2910-roller-servo.svg)](../../assets/images/software/team-2910-roller-servo.svg)
  <figcaption>
    The grey control modes are in both bases.
  </figcaption>
</figure>

| | Roller | Servo |
|---|---|---|
| **Class** | `RollerMotorSubsystem` | `ServoMotorSubsystem` |
| **Control modes** | velocity, duty cycle, voltage | position, Motion Magic, duty cycle, voltage |
| **Neutral mode** (default) | coast | brake |
| **Soft limits** | off | on, at the min and the max |
| **Homing** (finding its zero position) | no | `home()` |
| **Getters** | velocity | position |

What the control modes mean:

- **Duty cycle**: a percentage of the battery's voltage. `0.5` is half power.
- **Voltage**: a set number of volts, so the motor behaves the same as the
  battery drains.
- **Velocity**: a target speed. The TalonFX adjusts the power to hold it.
- **Position**: a target position. The TalonFX drives there and holds it.
- **Motion Magic**: a position target too, but the TalonFX speeds up,
  cruises and slows down on the way instead of jumping at full power. It's
  CTRE's feature for smooth arm and elevator moves.

Each base also has a **with followers** version
(`RollerWithFollowersSubsystem`, `ServoWithFollowersSubsystem`) for when
several motors drive one joint: one motor leads and the others copy it. The
flywheel uses one.

### Defining subsystems

The real subsystems are built from the bases in two ways.

<figure class="diagram" markdown="span">
  [![The SuperStructure sets the wanted state of four subsystems. SwerveSubsystem, the drivetrain, uses the CTRE swerve API. IntakeSubsystem is one file: it extends servo for the arm and has 2 rollers. HopperSubsystem is one file: it extends roller and has 3 more rollers. ShooterSubsystem extends SubsystemBase with no motor, and sets the wanted state of HoodSubsystem, which extends servo, and FlywheelSubsystem, a roller with followers](../../assets/images/software/team-2910-structure.svg)](../../assets/images/software/team-2910-structure.svg)
  <figcaption>
    Every arrow is a <code>setWantedState()</code> call, so orders only go
    down.
  </figcaption>
</figure>

**A simple subsystem is one file.** It extends the base of its main motor,
and keeps the other motors as fields. The intake's arm is a servo and its
two rollers are fields; the hopper is four rollers:

```java
public class IntakeSubsystem extends ServoMotorSubsystem {
    private final RollerMotorSubsystem rightRoller;
    private final RollerMotorSubsystem leftRoller;
```

```java
public class HopperSubsystem extends RollerMotorSubsystem {
    private final RollerMotorSubsystem rightFrontHopperMotor;
    private final RollerMotorSubsystem rightBackHopperMotor;
    private final RollerMotorSubsystem leftBackHopperMotor;
```

**A complex subsystem is split first, then combined.** The shooter has a
hood that moves to an angle and a flywheel that spins, and each needs its
own logic. So each gets its own file, built on its own base, and
`ShooterSubsystem` combines them into the part of the robot you'd point at:

```java
public class HoodSubsystem extends ServoMotorSubsystem { ... }

public class FlywheelSubsystem extends RollerWithFollowersSubsystem { ... }

public class ShooterSubsystem extends SubsystemBase {
    private final HoodSubsystem hood;
    private final FlywheelSubsystem flywheels;
```

`ShooterSubsystem` has no motor of its own. The hood's and flywheel's
`setWantedState()` have no `public`, so only code in the same package, the
`ShooterSubsystem`, can call them. Nothing else on the robot can move the
hood behind the shooter's back.

On top of everything sits the **SuperStructure**. It's also a subsystem,
but it has no motors: its job is to coordinate the intake, hopper, shooter
and swerve.

### A state machine inside every subsystem

Every layer, from the SuperStructure down to the hood, works the same way.
It has two enums:

- **`WantedState`**: what the layer above asked for. It's a variable that
  only changes when someone calls `setWantedState()`.
- **`SystemState`**: what the subsystem is actually doing this loop. The
  SuperStructure calls its own `CurrentState`.

Every loop, `periodic()` does two steps:

1.  **`handleStateTransition()`** picks the system state, from the wanted
    state and whatever else matters, like a sensor.
2.  **`applyStates()`** does what that system state needs: sets a motor, or
    sets the wanted state of the layer below.

Usually the system state just follows the wanted state, but not always. The
intake and the hood stay `HOMING` until they're homed, whatever is wanted.
The hopper is the clearest example: with the same wanted state, its two
distance sensors pick different system states.

<figure class="diagram" markdown="span">
  [![Three hoppers. Wanted DEFAULT with the hopper not full: OFF, 0 percent, nothing to do. Wanted DEFAULT with the hopper full and the feeder empty: PRELOADING at 7 percent, which moves fuel up to the feeder slowly. Wanted SHOOT, where the sensors don't matter: SHOOTING at 100 percent, feeding the shooter at full power](../../assets/images/software/team-2910-hopper.svg)](../../assets/images/software/team-2910-hopper.svg)
  <figcaption>
    A sketch, not the real robot. An orange light means the sensor sees
    fuel.
  </figcaption>
</figure>

| Wanted state | Sensors | System state | Hopper motors |
|---|---|---|---|
| `DEFAULT` | hopper full and feeder empty | `PRELOADING` | 7&nbsp;% |
| `DEFAULT` | anything else | `OFF` | 0 |
| `SHOOT` | don't matter | `SHOOTING` | 100&nbsp;% |

The SuperStructure never has to think about preloading. It asks for
`DEFAULT` or `SHOOT`, and the hopper handles the rest.

```java linenums="1"
public class HoodSubsystem extends ServoMotorSubsystem {
    private double desiredHoodAngle;
    private boolean isHomed;
    // Not shown: the HOMING_ constants passed to home()

    enum WantedState {
        OFF,
        HOME,
        HOLD_POSITION
    }

    private enum SystemState {
        OFF,
        HOMING,
        HOLDING_POSITION
    }

    private SystemState systemState = SystemState.OFF;
    private WantedState wantedState = WantedState.OFF;

    @Override
    public void periodic() {
        super.periodic();
        systemState = handleStateTransition();
        Logger.recordOutput("Hood/WantedState", wantedState);
        Logger.recordOutput("Hood/SystemState", systemState);
        applyStates();
    }

    private SystemState handleStateTransition() {
        if (!isHomed || wantedState == WantedState.HOME) {
            return SystemState.HOMING;
        }
        return switch (wantedState) {
            case OFF -> SystemState.OFF;
            case HOME -> SystemState.HOMING;
            case HOLD_POSITION -> SystemState.HOLDING_POSITION;
        };
    }

    private void applyStates() {
        switch (systemState) {
            case OFF -> setVoltageOutput(0.0);
            case HOMING -> {
                isHomed = home(
                        HOMING_DUTY_CYCLE,
                        HOMING_MECHANISM_VELOCITY_SETPOINT,
                        HOMING_SETTLE_TIME_REQUIRED,
                        HOMING_DEGREE_TO_RESET_TO);

                if (isHomed) {
                    systemState = SystemState.OFF;
                    if (wantedState == WantedState.HOME) {
                        wantedState = WantedState.OFF;
                    }
                }
            }
            case HOLD_POSITION ->
                    setMotionMagicSetpoint(desiredHoodAngle);
        }
    }

    void setWantedState(HoodSubsystem.WantedState wantedState) {
        if (this.wantedState != WantedState.HOME
                && wantedState == WantedState.HOME) {
            isHomed = false;
        }
        this.wantedState = wantedState;
    }

    void setDesiredHoodAngle(double desiredHoodAngle) {
        this.desiredHoodAngle = desiredHoodAngle;
    }
}
```

<div class="vscode__note" markdown>
**One state machine.** `periodic()` picks the system state, logs both
states, then applies it. Until the hood is homed, `handleStateTransition()`
returns `HOMING` no matter what's wanted, and `applyStates()` keeps calling
`home()`. `setWantedState()` and `setDesiredHoodAngle()` have no `public`,
so only `ShooterSubsystem` can call them.
</div>
</div>

```java linenums="1"
public class ShooterSubsystem extends SubsystemBase {
    private final HoodSubsystem hood;
    private final FlywheelSubsystem flywheels;

    public ShooterSubsystem(
            RobotState robotState,
            ConditionalCallbackManager callbackManager,
            MotorIO hoodIO,
            MotorIO leaderShooterRollerIO) {
        super("Serpentine");
        hood = new HoodSubsystem(
                robotState, callbackManager, hoodIO);
        flywheels = new FlywheelSubsystem(
                robotState, callbackManager, leaderShooterRollerIO);
    }

    public enum WantedState {
        OFF,
        HOME,
        RUN,
    }

    private enum SystemState {
        OFF,
        HOMING,
        RUNNING,
    }

    private SystemState systemState = SystemState.OFF;
    public WantedState wantedState = WantedState.OFF;

    @Override
    public void periodic() {
        systemState = handleStateTransition();
        applyStates();
    }

    private SystemState handleStateTransition() {
        return switch (wantedState) {
            case HOME -> SystemState.HOMING;
            case RUN -> SystemState.RUNNING;
            case OFF -> SystemState.OFF;
        };
    }

    private void applyStates() {
        switch (systemState) {
            case OFF -> {
                hood.setWantedState(HoodSubsystem.WantedState.OFF);
                flywheels.setWantedState(
                        FlywheelSubsystem.WantedState.OFF);
            }
            case HOMING -> {
                hood.setWantedState(HoodSubsystem.WantedState.HOME);
                flywheels.setWantedState(
                        FlywheelSubsystem.WantedState.SHOOT);
                setWantedState(WantedState.RUN);
            }
            case RUNNING -> {
                hood.setWantedState(
                        HoodSubsystem.WantedState.HOLD_POSITION);
                flywheels.setWantedState(
                        FlywheelSubsystem.WantedState.SHOOT);
            }
        }
    }

    public void setWantedState(WantedState wantedState) {
        this.wantedState = wantedState;
    }

    public boolean isAtShotConditions() {
        return hood.isHoodAtPosition()
                && flywheels.isShooterAtTargetRPM();
    }

    public void setShotConditions(
            double desiredRPM, double desiredAngle) {
        hood.setDesiredHoodAngle(desiredAngle);
        flywheels.setDesiredRPM(desiredRPM);
    }
}
```

<div class="vscode__note" markdown>
**The layer above.** Same pattern, but `applyStates()` never touches a
motor: it sets the wanted states of the hood and the flywheel. In `HOMING`
it tells the hood to home and moves itself straight on to `RUN`. The hood
keeps homing anyway, because its own state machine won't leave `HOMING`
until it's done.

```java linenums="1"
public class HopperSubsystem extends RollerMotorSubsystem {
    private final RollerMotorSubsystem rightFrontHopperMotor;
    private final RollerMotorSubsystem rightBackHopperMotor;
    private final RollerMotorSubsystem leftBackHopperMotor;
    private final RangeIO hopperRangeIO;
    private final RangeIO feederRangeIO;
    private boolean isHopperFull;
    // Not shown: the sensor inputs, the debouncer and
    // the constructor

    public enum WantedState {
        DEFAULT,
        SHOOT,
    }

    private enum SystemState {
        OFF,
        PRELOADING,
        SHOOTING,
    }

    private SystemState systemState = SystemState.OFF;
    private WantedState wantedState = WantedState.DEFAULT;

    @Override
    public void periodic() {
        super.periodic();
        hopperRangeIO.updateInputs(hopperRangeInputs);
        feederRangeIO.updateInputs(feederRangeInputs);
        isHopperFull =
                debouncer.calculate(hopperRangeInputs.isTripped);
        systemState = handleStateTransition();
        applyStates();
    }

    private SystemState handleStateTransition() {
        return switch (wantedState) {
            case DEFAULT -> {
                if (isHopperFull && !feederRangeInputs.isTripped) {
                    yield SystemState.PRELOADING;
                }
                yield SystemState.OFF;
            }
            case SHOOT -> SystemState.SHOOTING;
        };
    }

    private void applyStates() {
        switch (systemState) {
            case OFF -> setHopperDutyCycle(0.0);
            case PRELOADING -> setHopperDutyCycle(0.07);
            case SHOOTING -> setHopperDutyCycle(1.0);
        }
    }

    public void setWantedState(WantedState wantedState) {
        this.wantedState = wantedState;
    }

    private void setHopperDutyCycle(double dutyCycle) {
        setOpenLoopDutyCycle(dutyCycle);
        rightFrontHopperMotor.setOpenLoopDutyCycle(dutyCycle);
        rightBackHopperMotor.setOpenLoopDutyCycle(dutyCycle);
        leftBackHopperMotor.setOpenLoopDutyCycle(dutyCycle);
    }
}
```

**Sensors in the transition.** `handleStateTransition()` uses the two
CANrange distance sensors to choose between `PRELOADING` and `OFF`. The
debouncer only calls the hopper full once its sensor has seen fuel for
0.25&nbsp;s, so one ball bouncing past doesn't count. `setHopperDutyCycle()`
sets the motor this class extends, and the three roller fields.

## How a command runs

In 2910's code, a command's whole job is to set a wanted state. Here's the
whole trip from a button to a motor, one phrase per step:

<figure class="diagram" markdown="span">
  [![Once, when the button is pressed: 1, trigger call: the driver presses a button, and its binding runs a command. 2, set wanted state: the command sets what the robot should do, then ends right away. Every loop, in each subsystem's periodic(): 3, wanted state to system state: the subsystem picks what it will really do this loop. 4, apply state: it runs the code for that system state. 5, the state function calls the subsystem code: that code sets the wanted state of the layer below, or a motor. Then steps 3 to 5 happen again in the layer below, until a motor moves](../../assets/images/software/team-2910-command-phases.svg)](../../assets/images/software/team-2910-command-phases.svg)
  <figcaption>
    Steps 1 and 2 happen once. Steps 3 to 5 happen every loop, in every
    layer.
  </figcaption>
</figure>

### Example: pressing RB

RB is **score on the move**: shoot into the hub while driving. Here are the
same steps, with the real names from 2910's code:

<figure class="diagram" markdown="span">
  [![Pressing RB runs a command that calls setWantedStateCommand(SCORE_ON_MOVE) and ends. Every loop, the SuperStructure goes from wanted state SCORE_ON_MOVE to current state SCORING_ON_THE_MOVE and runs scoringOnTheMove(), which calls shooterSubsystem.setWantedState(RUN). The Shooter goes from RUN to RUNNING and its applyStates() calls hood.setWantedState(HOLD_POSITION). The Hood goes from HOLD_POSITION to HOLDING_POSITION and its applyStates() calls setMotionMagicSetpoint(angle) on the TalonFX, and the hood moves to the angle. Releasing RB runs onFalse, which sets DEFAULT_STATE](../../assets/images/software/team-2910-command-flow.svg)](../../assets/images/software/team-2910-command-flow.svg)
  <figcaption>
    Each band is one subsystem's <code>periodic()</code>, running every loop.
  </figcaption>
</figure>

1.  **Trigger call.** In `RobotContainer`, RB's `onTrue` runs a
    `Commands.runOnce(...)` command.
2.  **Set wanted state.** The command calls
    `superStructure.setWantedStateCommand(SCORE_ON_MOVE)` and ends in the
    same loop. It doesn't require any subsystem, so it never interrupts
    anything.
3.  **Wanted state to system state.** In the SuperStructure's `periodic()`,
    `handleStateTransitions()` turns `SCORE_ON_MOVE` into
    `SCORING_ON_THE_MOVE`.
4.  **Apply state.** `applyStates()` calls the function for that state,
    `scoringOnTheMove()`.
5.  **The state function calls the subsystem code.** `scoringOnTheMove()`
    works out the distance to the hub, looks up the flywheel speed and hood
    angle for that distance, and passes them on with
    `shooterSubsystem.setShotConditions(rpm, angle)`. It also sets the
    shooter to `RUN`, turns the swerve toward the hub, and sets the hopper
    to `SHOOT` once the shot is ready (and `DEFAULT` until then, so the
    hopper preloads while the robot aims).

**Then one layer down.** The shooter runs steps 3 to 5 in its own
`periodic()`: `RUN` becomes `RUNNING`, and `applyStates()` sets the hood to
`HOLD_POSITION`. The hood does the same, and ends with
`setMotionMagicSetpoint(desiredHoodAngle)`, a base method. Only now does a
motor move. The flywheel goes the same way, to its target speed.

**Letting go.** RB's `onFalse` sets the wanted state back to
`DEFAULT_STATE`, and the next loop every layer follows.

While RB is held, steps 3 to 5 repeat every loop with a new distance each
time, so the shot keeps up as the robot drives.

The few commands that keep running, like the swerve's default command,
work the same way: they pass the joystick to the swerve every loop and
never set a motor themselves. Autos are built from the same pieces: a
`runOnce` that sets a wanted state, then a `waitUntil(...)` that waits for
the robot to get there.

```java linenums="1"
        // Actions with superstates
        controller
                .rightBumper()
                .onTrue(Commands.runOnce(() -> superStructure
                        .setWantedStateCommand(SCORE_ON_MOVE)))
                .onFalse(Commands.runOnce(() -> superStructure
                        .setWantedStateCommand(DEFAULT_STATE)));

        controller
                .rightTrigger()
                .onTrue(Commands.runOnce(() -> superStructure
                        .setWantedStateCommand(PASS)))
                .onFalse(Commands.runOnce(() -> superStructure
                        .setWantedStateCommand(DEFAULT_STATE)));

        controller
                .leftBumper()
                .onTrue(Commands.runOnce(() -> superStructure
                        .setIntakeWantedState(
                                IntakeSubsystem.WantedState.INTAKE)))
                .onFalse(Commands.runOnce(() -> superStructure
                        .setIntakeWantedState(
                                IntakeSubsystem.WantedState.DEPLOY)));
    }
}
```

```java linenums="1"
    private CurrentState handleStateTransitions() {
        return switch (wantedState) {
            case STOPPED -> CurrentState.STOPPED;
            case DEFAULT_STATE -> CurrentState.DEFAULT_STATE;
            case HOME -> CurrentState.HOMING;
            case SCORE_ON_MOVE -> CurrentState.SCORING_ON_THE_MOVE;
            case PASS -> CurrentState.PASSING;
            // ...
        };
    }

    private void applyStates() {
        switch (currentState) {
            case STOPPED -> stopped();
            case DEFAULT_STATE -> defaultState();
            case HOMING -> homing();
            case SCORING_ON_THE_MOVE -> scoringOnTheMove(true);
            case PASSING -> passing();
            // ...
        }
    }

    private void scoringOnTheMove(boolean requireVisionObservation) {
        var translation = currentRobotPose.getTranslation();
        var targetRotation = targetHub.minus(translation).getAngle();

        var distance = getDistanceToCenterOfHub(translation);
        var rpm = container.getShooterInterpolation()
                .getInterpolatedRPM(distance);
        var angle = container.getShooterInterpolation()
                .getInterpolatedHoodAngle(distance);
        setShooterAndFeederShotConditions(rpm, angle);

        setSwerveToCalculatedState(
                targetRotation, SOTM_TRANSLATION_SCALAR);
        shooterSubsystem.setWantedState(
                ShooterSubsystem.WantedState.RUN);
        setFeederAndIntakeToCalculatedState(requireVisionObservation);
    }

    private void setFeederAndIntakeToCalculatedState(
            boolean requireVisionObservation) {
        if (isReadyToScore(requireVisionObservation)
                || isReadyToPass()) {
            hopperSubsystem.setWantedState(
                    HopperSubsystem.WantedState.SHOOT);
            setIntakeShootingState();
        } else {
            hopperSubsystem.setWantedState(
                    HopperSubsystem.WantedState.DEFAULT);
            intakeSubsystem.setWantedState(intakeWantedState);
        }
    }

        this.wantedState = superState;
```

### Compared with the usual style

On [Time-based to command-based](../time-based-to-command-based.md), holding
A runs a command that requires the intake and sets its motor every loop.
2910's code uses the same scheduler very differently:

| | Usual command-based | Team 2910 |
|---|---|---|
| **A button starts** | a command that requires a subsystem and runs while held | a command that sets a wanted state, then ends |
| **What sets the motors every loop** | the running command's `execute()` | each subsystem's `periodic()` |
| **Two buttons wanting the same subsystem** | the scheduler interrupts the older command | the wanted state that was set last wins |
| **When the button is released** | the command is cancelled, and the default command takes over | `onFalse` sets the wanted state back to the default |
| **Where the robot's logic lives** | spread over many small commands | the state machines, mostly in `SuperStructure` |

What this gives them:

- **One place decides.** Only the SuperStructure combines subsystems, and
  only the shooter can command the hood and flywheel, so it's easy to find
  which code moved what.
- **Logs that explain themselves.** Every layer logs its wanted state and
  its system state every loop, so after a match they can see what the
  driver asked for and what each part of the robot did about it.

What it costs:

- **A lot of code.** A new action means a new value in two enums, a line
  in each `switch`, and a state function. `SuperStructure.java` alone is
  about 700 lines.
- **The scheduler can't protect you.** Since the commands don't require
  subsystems, nothing stops code outside the SuperStructure from setting a
  wanted state. The team has to keep that rule themselves.

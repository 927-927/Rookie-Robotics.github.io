	- How subsystems are organized
		- subsystem bases
			- the subsystems are built on base templates (subsystems/base), so the motor code is written once:
				- roller (RollerMotorSubsystem): spins, no min/max position
					- velocity
					- duty cycle
					- voltage
				- servo (ServoMotorSubsystem): moves to a position between a min and a max
					- position control
					- motion magic
					- also duty cycle and voltage, same as roller
				- other differences
					- neutral mode: roller defaults to coast, servo to brake
					- soft limits: servo turns them on at its min/max, roller turns them off
					- homing: only servo has home(), which drives slowly into the hard stop until it stops moving, then sets that as its zero
					- different getters: roller gives velocity, servo gives position
				- each base also has a WithFollowers version, for several motors driving one joint (one leader, the rest follow it)
			- the bases never touch the TalonFX directly, they go through MotorIO (MotorIOTalonFX on the robot, SimMotorIOTalonFX in simulation)
		- definition of subsystems
			- simple subsystem -> one file
				- extends the base of its main motor, and keeps the other motors as fields
				- IntakeSubsystem: extends servo (the deploy arm), with two roller fields
				- HopperSubsystem: extends roller, with three more roller fields
			- complex subsystem -> first divide based on the base type (roller/servo) -> combine into real large subsystems on the robot with physical meanings
				- HoodSubsystem (servo) + FlywheelSubsystem (roller with followers) -> ShooterSubsystem
				- ShooterSubsystem extends plain SubsystemBase, it has no motor of its own
				- Hood and Flywheel's setWantedState() is package-private, so only ShooterSubsystem can control them
			- SuperStructure sits above all of them (Intake, Hopper, Shooter, Swerve) and coordinates the whole robot
		- internal state machine -> same mechanism as the larger one, but this is changed by the changes in the larger subsystems
			- every layer has a WantedState and a SystemState enum (SuperStructure calls its SystemState CurrentState)
			- the layer above sets the wanted state of the layer below: SuperStructure -> Shooter -> Hood / Flywheel
			- the system state doesn't always follow the wanted state
				- Intake and Hood stay HOMING until they're homed, whatever is wanted
				- Hopper: wanted DEFAULT -> PRELOADING if the hopper is full and the feeder is empty, otherwise OFF
	- How a command is run
		- Trigger call -> set wanted state -> wanted state to system state -> apply state -> state function calls the subsystem code
			- trigger call: in RobotContainer, e.g. rightBumper().onTrue(Commands.runOnce(() -> superStructure.setWantedStateCommand(SCORE_ON_MOVE))), and onFalse sets DEFAULT_STATE
			- set wanted state: the command only changes a variable and ends right away, it doesn't require any subsystem
			- wanted state to system state: every loop, SuperStructure.periodic() calls handleStateTransitions()
			- apply state: applyStates() runs the function for the current state, e.g. scoringOnTheMove()
			- state function calls the subsystem code: setWantedState() and setters like setShotConditions(rpm, angle)
		- each subsystem's periodic() repeats the same steps one layer down, until a base method (e.g. setMotionMagicSetpoint) sets the motor
		- the few commands that keep running (the swerve's default command, the X-button rotation snap) also only pass values to the swerve every loop, they never set a motor themselves
		- autos work the same way: runOnce(set wanted state) steps, put together with waitUntil(...) to wait for the robot to get there

As of November 2026 the FTC season is BIOBUZZ (2026-27, FIRST CANOPY season; kickoff 12 Sep 2026). That is too early for any top team to have published finished code for it, so the useful public code is from INTO THE DEEP (2024-25) and DECODE (2025-26). Most World Championship winners do not publish their code. GitHub searches found no public recent repos for 11260 Up-A-Creek (2025 Worlds winning-alliance captain), 30030/21087/11228 (2026 Worlds winners), 17792 (2026 Inspire), 18270, 20265 or 7172. The same is true of most of the suggested candidates (19234, 9889, 7236, 21229, 12051, 3965, 11115, 18172, 8417). 16379 KookyBotz' newest public repo is CenterStage (2023-24, last push 2024-07-01), and 10158's team repos end at CenterStage, so both fall outside the requested window.

The strong, recent, well-organized public repos come from teams with Worlds-level results:
- **11329 I.C.E. Robotics**: Hailstorm, DECODE. First pick on the Edison Division winning alliance at 2026 Worlds; Indiana State winning-alliance captain. Its README has a robot photo and the repo includes design docs.
- **23511 Seattle Solvers**: they maintain SolversLib. Their DECODE robot took 2nd place Inspire in the Lovelace Division at 2026 Worlds. Their INTO THE DEEP code is a clean command-based example.
- **19448 X BOTS**: DECODE; Control Award 1st, Lovelace Division, 2026 Worlds.
- **12808 RevAmped**: DECODE; Control Award 1st, Goodall Division, 2026 Worlds.
- **6165 MSET Cuttlefish**: INTO THE DEEP; Judges' Choice in the Jemison Division at 2025 Worlds.
- **14343 Escape Velocity**: INTO THE DEEP; WPILib-style FTCLib code.

Three architectural patterns show up:
1. A plain-Java "Robot" coordination class that owns subsystems, each with its own update() method, called from thin OpMode wrappers (11329).
2. FTCLib/SolversLib command-based code with a Robot singleton holding hardware, enum states per subsystem, and GamepadEx whenPressed bindings (23511, 19448, 14343).
3. A custom framework: an abstract Module class with ModuleState enums plus caching hardware wrappers (6165), or Hw* wrappers with a state graph and threads (12808).

Almost every team uses the same loop-time tricks: MANUAL bulk caching cleared once per loop, write caching (skip setPower/setPosition when the value change is below a tolerance), cached voltage reads, and passing the end-of-auto pose to TeleOp. Licensing caveat: every repo's LICENSE file is the FIRST SDK's BSD-3-Clause-Clear notice ("Copyright (c) 2014-2022 FIRST"), inherited from FtcRobotController. No team adds its own license, so the curriculum should link to the code and quote short attributed excerpts rather than copy whole files. Only 11329 includes robot photos (hailstorm.jpg, iceberg.jpeg), with no photographer credit, so ask the team for permission before reusing them.

REC: Feature three teams, in this order, as a progression from LinearOpMode to structured code.

**1. 11329 I.C.E. Robotics, Hailstorm (DECODE).** Teach this first because it needs no new library. Students see:
- a thin OpMode wrapper
- one TeleOp class shared by both alliances
- a Robot class that owns the subsystems and calls their update() each loop
- one class per subsystem, built from HardwareMap
- a Constants class with nested static classes
- FancyButton for rising and falling edges
- hand-written write caching plus MANUAL bulk caching
- saving the auto end pose for TeleOp

Its docs/robot.md explains in the team's own words why they moved from "every op mode initializes everything" to an integration layer. It is also the only candidate with a real README and robot photos, and it has a Worlds division win. Downsides: Robot.java is about 1,077 lines, the Pedro source is copied into the repo, and some files are experimental. Tell students to read Intake.java and MainTeleopBlue.java first and to skim Robot.java.

**2. 23511 Seattle Solvers, Into-the-Deep-2025.** This is the command-based step, using SolversLib, the library this team maintains. Teach:
- the Robot singleton holding all hardware
- the Globals constants file
- SubsystemBase classes whose states are enums (IntakePivotState, IntakeMotorState)
- command classes such as SetIntake and SetDeposit
- binding buttons declaratively in initialize() with whenPressed and InstantCommand, ConditionalCommand or UninterruptibleCommand
- SolversMotorEx write caching (tolerance 0.01)
- clearing only the Control Hub bulk cache
- committing the Pedro visualizer .pp files next to the autos
- the in-repo PIDF and servo tuning guides

Use the INTO THE DEEP repo, not Decode-2026: the DECODE repo is swerve with copied-in libraries and is too advanced. Credibility comes from the 2026 Worlds Lovelace Inspire 2nd and from authoring SolversLib. Warn that it was built against SolversLib 0.2.7 and the current version is 0.3.6.

**3. 6165 MSET Cuttlefish, 6165-IntoTheDeep.** This is the "build your own framework" contrast. It has an abstract Module class with ModuleState enums, a state machine per subsystem in which each enum value carries its servo or motor target, and EnhancedMotor/EnhancedServo wrappers whose comments explain write caching and voltage compensation. It earned Judges' Choice at 2025 Worlds. Downside: it is a 2-commit archived code dump, so there is no history to study.

**Alternate third pick: 19448 X BOTS (DECODE).** Choose this if you want a 2026 Worlds Control Award winner and the widely copied KookyBotz layout (common/commandbase/{commands,subsystems}, a Halo robot container, a Globals enum per mechanism). It overlaps 23511's pattern, though.

**Mention but do not feature:**
- 12808 RevAmped: Worlds Control 1st, but uses records and threads and depends on a LOCAL maven artifact, so it will not build.
- 14343 Escape Velocity: the WPILib-style mirror, useful for linking back to the FRC page, but its READMEs are jokes.
- 16379 KookyBotz CenterStage: historical template, last pushed 2024.

**Lessons that recur across all of them:**
- MANUAL bulk caching, cleared once per loop
- write caching
- one class per mechanism, with enum states
- a central Robot object (constructed object or singleton)
- a constants file
- binding buttons on rising edges
- passing the end-of-auto pose to TeleOp
- separate tuning and test OpModes

        || (corrected == 0.0 && cachedPower != 0.0)
        || (corrected >= 1.0 && !(cachedPower >= 1.0))
        || (corrected <= -1.0 && !(cachedPower <= -1.0))
        || Double.isNaN(cachedPower)) {
    cachedPower = corrected;
    dcMotorEx.setPower(corrected);
}
